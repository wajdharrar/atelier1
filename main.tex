\section{Introduction}

Ce rapport analyse l'architecture logicielle du système
\emph{Parallel Collective Tiny Deep Learning System for Face and Object
Reidentification in Uncontrolled Environments},
noté \textbf{DNN//\(^{*}\)Tcs}, puis propose une architecture alternative
répondant aux faiblesses identifiées. La démarche suit trois étapes~:

\begin{enumerate}
    \item analyse détaillée de l'architecture existante (structure, forces,
    faiblesses) ;
    \item proposition d'une nouvelle architecture basée sur les principes des
    \textbf{systèmes répartis} et des \textbf{microservices} ;
    \item modélisation de cette architecture selon les quatre niveaux du
    \textbf{modèle C4} (contexte, conteneurs, composants, code), intégrant la
    gestion de l'hétérogénéité matérielle sans OS et la synchronisation temporelle, avec des
    pistes de validation.
\end{enumerate}

% =====================================================================
\section{Analyse de l'architecture existante}

\subsection{Présentation générale}

Le système proposé par les auteurs combine trois niveaux d'exécution pour
détecter et reconnaître, en temps réel, des visages, émotions, genres et
objets~:

\begin{itemize}
    \item \textbf{Client} (\texttt{DNN//\(^{*}\)c}) : version « lite »
    destinée à un appareil mobile ou des lunettes connectées. Chaque
    service (visage, émotion, genre, objet) tourne dans un processus
    séparé, avec un nombre de neurones par couche limité par le matériel ;
    \item \textbf{Serveur} (\texttt{DNN//\(^{*}\)s}) : version précise,
    exécutant \texttt{k1} versions de réseaux de neurones profonds et
    \texttt{k2} versions d'algorithmes de \textit{Machine Learning} en
    parallèle pour chaque service ;
    \item \textbf{Objets connectés Tiny} (micro-contrôleurs de type
    Arduino) : envoient directement identité, position et dimensions des
    objets réels, sans passer par l'analyse d'image.
\end{itemize}

Un \textbf{gestionnaire collectif parallèle}
(\texttt{MSParallelCollectiveManager}), piloté par une approche TinyML,
fusionne les résultats des trois sources via un opérateur \(\otimes\)
(structure d'évaluation \(S\) : ensemble ordonné, comparateur \(\leq\),
opérateur commutatif, associatif et monotone) afin de sélectionner, en
temps réel, le résultat le plus fiable.

\noindent \textbf{Point clé de l'analyse} : la validation expérimentale
(section 6 de l'article) ne teste \textbf{que la partie serveur}, exécutée
sur un unique ordinateur portable (Dell Vostro 3400, Intel i3-1115G4,
4 cœurs, 12 Go de RAM) via du \emph{multiprocessing} local --- un
processeur (cœur) affecté à chaque service. Le client mobile n'est jamais
implémenté (\og \emph{a lite version of a server version} \fg{}) et les
objets Tiny/Arduino sont \textbf{simulés}, non connectés physiquement. Le
schéma client-serveur-Tiny reste donc, pour l'essentiel, une proposition
théorique.

\subsection{Forces de l'architecture existante}

\begin{itemize}
    \item \textbf{Réduction des erreurs de classification} : la fusion de
    plusieurs versions de modèles avec les données de vérité terrain des
    objets Tiny permet d'atteindre 100~\% de précision sur les jeux de
    données testés (Tableaux 1 à 3 de l'article) ;
    \item \textbf{Dimensionnement théorique justifié} : le nombre optimal
    de processeurs est calculé formellement (théorèmes 1 à 4, lois
    d'Amdahl et de Brent) en fonction du nombre de neurones par couche ;
    \item \textbf{Séparation logique lite/précis} : la distinction entre
    une version cliente allégée et une version serveur plus précise est
    pertinente pour des contraintes matérielles embarquées ;
    \item \textbf{Complémentarité multi-modèles} : faire tourner plusieurs
    architectures (CNN, YOLOv8 dans ses différentes tailles, LBPH) en
    parallèle et comparer leur confiance limite le risque de dépendre d'un
    seul modèle défaillant.
\end{itemize}

\subsection{Faiblesses de l'architecture existante}

\begin{itemize}
    \item \textbf{Confusion service / processus} : les \og micro-services
    \fg{} (\texttt{MS*}) sont en réalité des processus systèmes qui
    s'appellent directement en mémoire partagée (\texttt{RunProcess2(...)})
    et non des services réseau découplés avec un contrat d'interface ---
    ils ne sont donc ni déployables ni scalables indépendamment ;
    \item \textbf{Scalabilité strictement verticale} : le dimensionnement
    \(P^{*} = f(\text{neurones}, k_1, k_2)\) suppose une seule machine
    multi-cœurs ; aucune notion de cluster, de répartition de charge ou
    d'auto-scaling horizontal n'est envisagée ;
    \item \textbf{Couplage fort du gestionnaire de fusion} : le
    \texttt{Manager} appelle directement \texttt{VersionOfServce(i)}, sans
    interface d'abstraction entre le sélecteur et les modèles évalués ;
    \item \textbf{Absence de tolérance aux pannes et de synchronisation} : aucun mécanisme de
    \emph{retry}, de synchronisation d'horloge réseau, ou de redondance n'est décrit
    en cas de défaillance d'un service ou d'un objet Tiny ;
    \item \textbf{Gestion de versions de modèles informelle} : les
    versions \(k_1\)/\(k_2\) sont lancées \og en dur \fg, sans registre de
    modèles ni stratégie de déploiement progressif (\emph{canary}) ;
    \item \textbf{Sécurité et observabilité absentes} : le papier ne
    mentionne ni authentification, ni traçabilité, ni supervision ;
    \item \textbf{Écart entre architecture proposée et architecture
    validée} : comme relevé ci-dessus, le client mobile et les objets
    Tiny ne sont jamais réellement testés en conditions distribuées.
\end{itemize}

\section{Solution proposée}

\subsection{Principes directeurs et justification du système réparti}

Pour résoudre les faiblesses identifiées, nous proposons de repenser l'architecture sous la forme d'un \textbf{système réparti hétérogène}. 

\noindent \textbf{Justification de la refonte distribuée :} Les objets Tiny (microcontrôleurs de type Arduino, STM32, ESP32) se caractérisent par l'\textbf{absence totale de système d'exploitation classique (Bare-Metal)}. Ils n'offrent ni gestionnaire de processus, ni mémoire virtuelle, ni pile d'abstraction logicielle haut niveau. Historiquement, l'introduction des couches d'OS dans les architectures informatiques visait à faciliter la communication inter-processus (IPC) entre l'utilisateur et la machine, ainsi qu'entre deux machines distantes. 

En l'absence d'OS sur les nœuds Tiny, nous devons revenir aux fondamentaux des \textbf{systèmes répartis} :
\begin{itemize}
    \item \textbf{Couche de middleware distribué (Abstraction matériel/OS)} : Mettre en place un protocole d'interopérabilité (MQTT / CoAP / gRPC-Lite) qui masque l'absence d'OS des objets Tiny et uniformise le passage de messages entre les nœuds nus (Bare-metal) et les nœuds dotés d'OS (serveurs Cloud/Edge) ;
    \item \textbf{Services indépendants et scalabilité horizontale} : Remplacer le scale-up mono-machine par un découplage en microservices conteneurisés (Kubernetes) sur la partie serveur ;
    \item \textbf{Communication asynchrone et tolérante aux pannes} : Utiliser un broker de messages (Kafka/RabbitMQ) pour absorber la volatilité et la latence réseau des nœuds Tiny sans bloquer le serveur ;
    \item \textbf{Synchronisation temporelle distribuée} : Introduire un composant de synchronisation d'horloge (horloges logiques ou vectorielles) pour aligner temporellement les données transmises par les objets Tiny avec les flux d'images traités par le serveur.
\end{itemize}

\noindent \textbf{Extrait de code (Python) : Synchronisation distribuée et fusion :}

\begin{lstlisting}[language=Python]
from abc import ABC, abstractmethod
from typing import Dict

class VectorClockManager:
    """Gere l'horloge vectorielle pour ordonner les evenements dans le systeme reparti."""
    def __init__(self, node_id: str):
        self.node_id = node_id
        self.clock: Dict[str, int] = {node_id: 0}

    def increment(self):
        self.clock[self.node_id] = self.clock.get(self.node_id, 0) + 1

    def update(self, remote_clock: Dict[str, int]):
        """Met a jour l'horloge locale selon la regle de Lamport/Vector Clocks."""
        for node, count in remote_clock.items():
            self.clock[node] = max(self.clock.get(node, 0), count)
        self.increment()

    def is_causally_aligned(self, clock_a: Dict[str, int], clock_b: Dict[str, int], max_drift: int = 2) -> bool:
        """Verifie si deux evenements (Tiny IoT vs Inferred Frame) sont temporellement proches."""
        diff = abs(clock_a.get(self.node_id, 0) - clock_b.get(self.node_id, 0))
        return diff <= max_drift


class IFusionStrategy(ABC):
    @abstractmethod
    def combine(self, result_a, result_b):
        raise NotImplementedError


class TinyValidatedFusion(IFusionStrategy):
    def __init__(self, tiny_data, clock_manager: VectorClockManager):
        self.tiny_data = tiny_data
        self.clock_manager = clock_manager

    def combine(self, result_a, result_b):
        # Verification de la synchronisation causale avec les objets Tiny sans OS
        if self.tiny_data.is_available():
            if self.clock_manager.is_causally_aligned(result_a.clock, self.tiny_data.clock):
                return self.tiny_data.to_result() # Priorite a la verite terrain Tiny
        
        # En cas de desynchronisation ou d'absence Tiny, arbitrage par score de confiance
        return result_a if result_a.confidence >= result_b.confidence else result_b


class EnsembleService:
    def __init__(self, strategy: IFusionStrategy, node_id: str):
        self.strategy = strategy
        self.clock_manager = VectorClockManager(node_id)

    def evaluate(self, results: list):
        if not results:
            return None
        self.clock_manager.increment()
        fused = results[0]
        for r in results[1:]:
            fused = self.strategy.combine(fused, r)
        return fused

\section{Conclusion}

L'application du \textbf{modèle C4} combinée aux principes des \textbf{systèmes répartis} a permis d'évoluer d'un prototype monolithique local vers une architecture distribuée, robuste et prête pour le déploiement réel. 

En prenant en compte la contrainte matérielle majeure du système --- à savoir l'absence d'OS sur les objets Tiny (exécution bare-metal) --- nous avons réintégré une couche middleware distribuée et un composant de \textbf{synchronisation temporelle (horloges vectorielles)}. Cette approche comble le fossé historique de communication entre les machines sans OS et l'infrastructure serveur. Enfin, le découplage en microservices et l'usage de patrons de conception flexibles (comme le patron Strategy) garantissent une scalabilité horizontale, une tolérance aux pannes efficace et une maintenance simplifiée du système global.
